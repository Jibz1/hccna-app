# Benchmark runbook (phase 1)

How to set up the side-by-side comparison on Railway, run it, and tear it down. Design and
decisions: `docs/superpowers/specs/2026-10-13-server-rust-benchmark-design.md`. Record numbers in
[`RESULTS.md`](RESULTS.md).

Nothing here touches the live `hccna-backend` service, `api.hccnj.org`, or production Redis. Only
the four new services below take load. The tooling enforces part of that: `k6/lib.js`, `diff.ts`
and `redis-stats.ts` refuse targets named `hccna-backend`, `hccna-backend-production`,
`*.hccnj.org` and anything starting with `hccna-redis` (`k6/guard.js`).

| What | Where |
|---|---|
| Operation corpus | `operations.json`, generated by `extract-operations.ts` from the mobile Relay artifacts |
| Load scenarios | `k6/warm.js`, `k6/resolver.js`, `k6/cold.js` (shared code in `k6/lib.js`) |
| k6 image | `Dockerfile` (the `hccna-bench` service) |
| Correctness diff | `diff.ts` (Bun, runs on your machine) |
| Cache verification | `redis-stats.ts` (Bun, reads the bench Redis) |
| Checks | `bun apps/server-rs/bench/extract-operations.ts --check`, `bun test apps/server-rs/bench`, `k6 inspect k6/<scenario>.js` |

Commands below use the Railway CLI. Flags are those of the version pinned in the workflows
(`RAILWAY_CLI_VERSION`); run `railway <command> --help` if one differs. Everything can also be done
in the dashboard.

### Link the CLI once, for the whole window

The Railway CLI keeps its project link per directory, and `railway variables`, `railway connect`,
`railway logs`, `railway redeploy` and `railway up` all need it (they take `--service` and
`--environment` but no `--project`). Link once now, from the checkout you run this runbook from,
and unlink only in section 8:

```sh
railway login
railway link --project c56f6ebf-17ff-41af-8740-70e769720898 --environment production
railway status                          # confirm: Apps Backend, production
```

If `link` asks for a service, choose none: every command below names its service with `--service`.
Run every `railway` command from this directory. The one exception is the TS deploy in section 5,
which runs from its own checkout of `main` and links that directory too.

Two things to settle first:

1. **Private networking.** The harness reaches the servers at `*.railway.internal`, and the Rust
   gateway forwards to TS the same way. The TS server binds `0.0.0.0`
   (`apps/server/src/effect/AppConfig.ts`, and Bun's default for the metrics server), and the
   Rust server binds `::`. On 2026-10-17 the `production` environment resolved those names to IPv6
   and IPv4, and TS answered over IPv4 from inside the project. Railway environments created before
   2025-10-16 resolve them to IPv6 only. If the project ever moves to such an environment,
   `hccna-backend-ts-bench` is unreachable from `hccna-bench` and its `/metrics` cannot be scraped.
   You find out at the first run: `setup()` fails with `.../readyz answered no response`.
   Fallbacks, in order of preference:
   - Use the public Railway domains for both targets (`TARGET_URL=https://<domain>`), so both
     servers pay the same edge cost, and say so in `RESULTS.md`. Latencies then include the edge
     proxy.
   - Leave `TARGET_METRICS_URL` unset for TS and take its CPU and memory from Railway only. The
     Redis checks in section 6 do not need the servers' `/metrics`.
2. **Anonymous accounts.** Each run signs up anonymous users in the production Firebase project,
   as the app does on first launch: 1 per `warm` or `cold` run, 4 per `resolver` run, 1 per
   `diff.ts` run. A full program (section 6) creates about 30. They have no profile and cost
   nothing, and section 8 removes them. If sign-up returns an API key restriction error, use a key
   that allows Identity Toolkit calls without a browser referrer or app identity (Google Cloud
   console, Credentials), or create a dedicated key limited to the Identity Toolkit API. The key is
   sent in an `x-goog-api-key` header, never in a URL.

Load goes to Strapi, Firebase and Postgres, which production also uses. Schedule runs off peak
(not around Sunday services or Wednesday evenings, Eastern time). The rates are capped in the
scripts for the same reason: `warm` 100 rps (cache hits only), `resolver` 20 rps, `cold` 2 rps.

**Do not merge Rust app or deployment workflow changes into `main` during a benchmark window.**
`.github/workflows/server-rs.yml` redeploys `hccna-backend-rs` on every push that touches
`apps/server-rs/**` or `.github/workflows/server-rs.yml`, which restarts the target in the
middle of a run (`valid` turns false, and the caches are cold again). Pause merges, or set
`SERVER_RS_DEPLOY_ENABLED` to `false` for the window. Pushes to `main` do not redeploy the bench TS copy (it is deployed by hand).

**The Statsig gate `server_rs_serve_locally` must be on for every run.** Since the gateway
(`docs/superpowers/specs/2026-10-14-server-rs-parity-design.md`), `hccna-backend-rs` answers the

unreachable, the service forwards every request to `TS_ORIGIN_URL`: the TS bench copy while the
window's setting from section 5 holds, otherwise production `hccna-backend`. The benchmark would
then measure TS behind an extra hop, and with the production value it would also put its load on
production.
Check it before any load (section 6, "Before any load"), with the link from section 0. The request
below counts as served traffic, so after the per-run restarts read the start-up log only (section 6,
"One run", step 3):

```sh
RS_URL=https://<rs domain>
RID="bench-gate-check-$(date +%s)"
curl -s -o /dev/null -H 'content-type: application/json' -H "x-request-id: $RID" \
  --data '{"query":"query CoreDataQuery { core { giving { copy } } }"}' "$RS_URL/graphql"

railway logs --service hccna-backend-rs --environment production --since 5m --json -n 5000 | grep -F "$RID"
```

(`railway logs --service hccna-backend-rs --environment production --since 1d --json -n 5000 | grep -F "Statsig initialized"`),
Statsig failed at boot and the service forwards until it restarts: redeploy it.

Merge a change to `apps/server-rs/**` into `main`. The `server-rs` workflow checks, builds the image,
runs `railway up --ci --service hccna-backend-rs --environment production` and then calls
`/readyz`. Record the commit SHA. To deploy by hand from a checkout of that branch instead:

```sh
# from the linked checkout, on main
railway up --ci --service hccna-backend-rs --environment production
```

### Post-deploy check: the rate limiter must not trust a forged `X-Real-IP`

The Rust server keys its per-IP rate limiter on Railway's `X-Real-IP` header, falling back to the
peer address. That is only safe if Railway's edge **overwrites** a client-supplied `X-Real-IP`. Check
it before raising `GRAPHQL_RATE_LIMIT_RPS`, with the limit still at its default of 20 requests per
second. The limiter runs before authentication, so unauthenticated requests are enough. Send 40
requests at once, each with a different forged `X-Real-IP`:

```sh
RS_URL=https://<rs domain>
seq 1 40 | xargs -P 40 -I{} curl -s -o /dev/null -w '%{http_code}\n' -X POST "$RS_URL/graphql" \
  -H 'content-type: application/json' -H 'X-Real-IP: 198.51.100.{}' \
  --data '{"query":"query Probe { __typename }"}' | sort | uniq -c
```

- **Expected:** some `429` responses (about 20 of the 40 or more). All 40 requests came from one
  machine, so they share one bucket if the server uses the real client address. If the forged
  header were honoured, each request would have its own bucket and none would be limited.
- **Failure:** no `429` among the responses. Railway is passing the forged header
  through, so the limiter can be bypassed by anyone who can reach the service. Keep the limit at
  its default, do not raise it, and report it to the owner before going further.
- If the Rust request log records a client address, also confirm it shows your real address, not
  `198.51.100.x`.

Then set `GRAPHQL_RATE_LIMIT_RPS=100000` on `hccna-backend-rs` and let it redeploy.

## 6. Run order

### Before any load

1. `bun apps/server-rs/bench/extract-operations.ts --check` and `bun test apps/server-rs/bench`
   pass on the commit you deploy.
2. Both servers are ready, with the same resource limits, one replica, us-east4, and the
   section 3 check shows the bench Redis for both. `hccna-backend-rs` forwards to the bench copy,
   not to production. What this prints must contain `hccna-backend-ts-bench`. Stop if it prints
   `unset` or a production `hccna-backend` domain, and set it as in section 5:

   ```sh
   railway variables --service hccna-backend-rs --environment production --json | jq -r '.TS_ORIGIN_URL // "unset"'
   ```
3. **Flush and restart.** Flush the bench Redis and restart both servers (steps 1 and 2 of "One
   run" below, for both).
4. **Check the Rust gate.** Confirm `server_rs_serve_locally` is on and the Rust service is
   answering locally: run the section 3 gate check, the `/graphql` request and the log search.
   A request is fine here because nothing has been measured yet, and the restart in step 2 of
   each "One run" resets the counters. **Stop** if the request log line shows `route` as
   `forward`, or if the start-up log has no `Statsig initialized` line; fix the gate or redeploy,
   then repeat steps 3 and 4.
5. **Correctness first.** Compare the two servers:

   ```sh
   TS_URL=https://<ts-bench domain> RS_URL=https://<rs domain> \
     bun apps/server-rs/bench/diff.ts            # add --thorough for sermon paging and unknown slugs
   ```

   (`FIREBASE_WEB_API_KEY` is already exported from the prompt in section 0.) It prints one verdict
   per case and the JSON paths that differ (never values). A case **fails** when the responses
   differ and also when a server answers with an error (non-200, GraphQL `errors`, or a
   `...FetchError` / `...NotFoundError` result), even if both do the same: two equally broken
   servers prove nothing. Only the deliberate edge cases in `--thorough` (first 0, over 100,
   invalid cursor, unknown event slug) may error, and then must match. A case that could not be
   built, for example `EventDetailQuery` when there are no upcoming events, is printed as `SKIP`
   and a `WARNING` line says what was not compared. Bodies and the full report go to
   `$TMPDIR/server-rs-diff-<time>/` (owner-only permissions); the script refuses an `--out` inside
   the repository. `verseOfTheDayV2.verseId` is ignored when both sides return the `firebase-vod-`
   fallback. Do not benchmark servers that disagree; fix the Rust side or record why the
   difference is expected.
6. Delete the report directory when you are done reading it: it is real CMS content.
7. `diff.ts` leaves both servers non-fresh. Do the full flush and restart again before the first
   run (the `cold` run is marked invalid otherwise).

### One run

Every run starts from the same state, so the order of runs cannot favour a target.

1. **Check the target Redis, then flush it.** Re-run the section 3 check; it must show
   `hccna-bench-redis` for both servers. Then, naming the service explicitly (never `hccna-redis`):

   ```sh
   railway connect hccna-bench-redis      # opens redis-cli; then: DBSIZE, FLUSHALL, DBSIZE, exit
   ```

   `DBSIZE` should be a few hundred keys at most before the flush and `0` after. Do not run
   `FLUSHALL` in any other session.
2. Restart the target server so its in-process caches are empty (`railway redeploy --service
   <name> --yes`, or Restart in the dashboard). Wait until its deployment is healthy.
3. **For the Rust target, check the start-up log now, after this restart** (skip it for TS).
   Statsig can fail at any boot, and a service that booted without it forwards every request to
   `TS_ORIGIN_URL` (the bench copy, per "Before any load" step 2); the check from before the restart
   says nothing about this one, and `hccna-bench` guards only its own `TARGET_URL`, not where the
   target forwards.
   Confirm that this deployment logged `Statsig initialized` (use `--since` with a window that
   covers the restart, and check that the line's timestamp is after it):

   ```sh
   railway logs --service hccna-backend-rs --environment production --since 10m --json -n 5000 | grep -F "Statsig initialized"
   ```

   **Abort the run, and do not point `hccna-bench` at the target**, if that prints nothing or if
   `grep -F "Statsig initialization failed"` on the same logs prints a line. Fix the gate or
   redeploy, then start again from step 1. Send no `/graphql` request in this step: a request
   would spoil the `cold` run's freshness (`INVALID RUN`). The `route` check lives in step 6.
4. **Snapshot the Redis counters** (see "Check the cache behaviour" below), point `hccna-bench` at
   the target and run. Changing variables triggers a new deployment, which runs the scenario once:

   ```sh
   railway variables --service hccna-bench \
     --set SCENARIO=warm --set TARGET_NAME=rs \
     --set TARGET_URL=http://hccna-backend-rs.railway.internal:8080 \
     --set TARGET_METRICS_URL=http://hccna-backend-rs.railway.internal:9184
   ```

   To repeat without changing anything, redeploy: `railway redeploy --service hccna-bench --yes`.
5. When the deployment has exited, **snapshot the Redis counters again**, then read the result.
   stdout is JSON Lines, one object per line with a `type`; save it outside the repo:

   ```sh
   mkdir -p "$TMPDIR/bench"
   railway logs --service hccna-bench | grep '^{"type"' > "$TMPDIR/bench/<pass>-<scenario>-<target>.jsonl"
   ```

   Progress and a readable table go to stderr (they appear in the same log stream). An invalid run
   prints `INVALID RUN: <reasons>` first.
6. Check the run was valid (below) and the cache behaved as expected, then copy the numbers into
   `RESULTS.md`. **For the Rust target the run is also invalid if any request was forwarded
   during it**: `gateway_requests_total{route="forward"}` (summed over its status classes) on the
   target's `/metrics` (`http://hccna-backend-rs.railway.internal:9184/metrics`, private network
   only) must be 0 at the end of the run. The counter restarts at 0 with the step 2 restart, and
   step 3 sends no request. The `server` line does not carry that counter.
   Without a shell inside the project, search the target's request log for the run window instead
   (`railway logs --service hccna-backend-rs --environment production --since <window> --json -n 5000 | grep -c 'route[^a-z]*forward'`
   must print 0); `-n 5000` returns only the newest lines, so on a long run that covers its end
   only. Any forwarded request means the run measured the TS bench copy behind an extra hop
   (and, had `TS_ORIGIN_URL` not named the bench copy, put load on production `hccna-backend`): discard the run
   and find out why before the next one.

### Check the cache behaviour (bench Redis)

Both servers share the bench Redis and Redis counts the same way for both, so it is the one place
to verify cache hits and misses on TS and Rust alike. (The TS `/metrics` has `service_request` only
for Strapi, CCB and Castr: no Firebase, Postgres or Firestore counters, so those cannot be compared.)
Take `INFO commandstats` and `DBSIZE` before and after each run:

```sh
export BENCH_REDIS_URL="$(railway variables --service hccna-bench-redis --json | jq -r .REDIS_PUBLIC_URL)"
bun apps/server-rs/bench/redis-stats.ts snapshot --label=before --out="$TMPDIR/bench/before.json"
# ... the run ...
bun apps/server-rs/bench/redis-stats.ts snapshot --label=after  --out="$TMPDIR/bench/after.json"
bun apps/server-rs/bench/redis-stats.ts delta "$TMPDIR/bench/before.json" "$TMPDIR/bench/after.json" --requests=<GraphQL requests of the run>
```

`<GraphQL requests>` is `server.graphql.requests` from the run's `server` line. The URL is read
from Railway into the environment, never typed or printed; the script refuses a production Redis
URL and is read-only. By hand, the same numbers are in the `railway connect hccna-bench-redis`
session: `INFO commandstats`, `DBSIZE`, and `redis-cli --scan --pattern 'rs:graphql:response-cache:result:v2:*' | wc -l` against the
proxy URL.

What to expect (a mismatch means the run did not measure what its name says):

| Counter | Expected |
|---|---|
| `incr` | About one per GraphQL request: the per-IP rate limiter runs for every request on both servers. If it is far from the request count, the window is not the run, or another client is using the Redis |
| `warm`: `setex` | A small constant, not proportional to requests. The "before" snapshot is taken before the k6 deployment starts, so the window includes `setup()`'s priming pass: expect tens to a few hundred writes (more on TS, which also writes entity-index entries), then nothing during the load except after a TTL expires (10 min for most fields) |
| `warm`: `get` | Small: about one per cache key per 30 s, when the in-process tier's TTL cap (30 s) forces a re-read. Not proportional to requests |
| `resolver`: new response entries | **The cross-server check.** `keys` for `graphql:response-cache:result:v2:*` (TS) and for `rs:graphql:response-cache:result:v2:*` (Rust) each grow by about **80%** of the requests (the 45% sermon plus 35% campuses requests always miss) |
| `resolver`: `rs:*` and `cms-v5:*` | Rust `rs:*` is every key the Rust server wrote, not response entries: it grows by about **125%** of the requests, the 80% response entries plus about 45% record-cache entries (one per sermon request, 70 min TTL, shown by `rs:cms-v5:*`) plus a handful of core, VOD, CCB and generation keys. TS `cms-v5:*` shows the same record entries (about 45%) |
| `resolver`: `setex`, `get`, `ttl` | **Do not compare across servers.** Rust `setex` is about 125% of the requests (response plus record entries). TS `setex` is higher: it adds one entity-index entry per entity in each response (the Rust server deliberately does not port the entity index), and TS `get` is inflated by the matching entity-index `GET` per entity per miss. TS also issues a `TTL` read per rate-limited request. Use `incr` and the new-entry counts above |
| `cold`: `setex` | One per first-touched key, then flat in later passes |
| `dbsize` delta | The number of new cache entries the run created |

**Strapi in the resolver run.** Only the sermon page requests reach Strapi: about **45%** of the
requests, since each (count, cursor) pair is a distinct Strapi query. `CampusesQuery` misses are
served by the Strapi record cache, and the event operations have a handful of keys. Compare the
server `strapiRequests` (from each server's `/metrics`, the `strapi-v5` service) with about 45% of
`server.graphql.requests`, not with the request count.

### The program

**Idle first (once).** After a fresh restart of both servers, leave them with no traffic for 30
minutes and record Railway CPU and memory for that window.

Then each scenario on each target, one target at a time, never both at once. Do pass A, then pass B
with the targets reversed:

| Pass A | Pass B (reversed) |
|---|---|
| warm on rs, warm on ts | warm on ts, warm on rs |
| resolver on rs, resolver on ts | resolver on ts, resolver on rs |
| cold on rs, cold on ts | cold on ts, cold on rs |

Each run is about: `warm` 4.5 minutes, `resolver` 5 minutes, `cold` under a minute. Allow for the
restarts between them.

### What each scenario measures and how to read it

| Scenario | Isolates | Notes |
|---|---|---|
| `warm` | HTTP handling, parsing, the response-cache lookup, serialization | Fixed variables; `setup()` primes every operation once, so nearly every request is a cache hit. Steps are separate `constant-arrival-rate` scenarios (`step1_10rps`, ...); each `step` line carries its `startedAt` and `endedAt` |
| `resolver` | Authentication (one Firebase lookup per cache miss), execution, record caches, JSON transforms | `SermonsItemsRefetchQuery` uses each `(count 1..50, discovered cursor)` pair at most once and `CampusesQuery` a unique `preferredCampus`, so both miss the response cache every time. Event operations vary slugs and tokens, so only their first request per key misses. Operations without variables (core, thoughtOfGod, ccbFormsV2, verseOfTheDayV2) are covered by `cold`. Expected Strapi share: about 45% (above). `setup()` aborts when the discovered cursors cannot cover the planned sermon requests |
| `cold` | Upstream-bound latency | Right after the flush and restart. Pass 1 of the 11 operations is the cold measurement; `later` passes show the same requests warm. `setup()` makes the first `CampusesQuery` and `LatestEventsQuery` requests itself (it discovers no sermon cursors); their timings are in the `setup` line as `discovery`. The run is invalid (`fresh: false`) if the target had already served GraphQL requests |

The request sequence depends only on `SEED` and the discovered data, not on the clock, so the same
`SEED` gives both targets the same sequence.

### Output lines

`run` (config, iterations, `droppedIterations`, `fresh`, `valid`, `invalidReasons`, overall latency,
gzip rate, `startedAt` of setup and `loadStartedAt` / `loadEndedAt` of the load), then
`step` (warm) and `operation` / `pass` / `operation-first` / `operation-later` lines (requests,
`failedRate` for HTTP errors, `graphqlOkRate` for responses that are HTTP 200 with no GraphQL
`errors` and no `...FetchError` / `...NotFoundError` result, latency in ms, `responseCharsAvg`:
average decoded body length in characters, not bytes on the wire), `setup` (what discovery found,
`skipped` operations, discovery timings), and `server` (the target's own `/metrics` before and
after). If setup fails, the only line is `{"type":"error"}` and k6 logged the cause above it.

A run is **valid** only if `valid` is true. It is false when any of these holds: iterations were
dropped (the generator could not keep the arrival rate), `graphqlOkRate` is below 1 for the load
(including FetchError / NotFoundError results), no load request was made, a cold run was not fresh,
or a server counter went backwards (the target restarted mid-run). `invalidReasons` says which.
Redo an invalid run. `setup.skipped` lists operations that could not run on this target (for
example `EventDetailQuery` with no upcoming events); say so in `RESULTS.md`.

### Server-side metrics: what each server exposes

- **Rust** (`src/metrics.rs`): one registry with the TS metric names, plus `process_*` (RSS, CPU
  seconds, threads, open fds) on Linux.
- **TS** (`src/app.ts`, `metricsApp`): prom-client counters without `_total`, then the Effect/OTel
  copy (counters with `_total`, histograms repeated). The parser keeps the first block of each
  family so nothing is counted twice. **TS exposes no `process_*` metrics**
  (default collection is off), so `server.process` is null for it. Its `service_request` counters
  exist only for `strapi-v5`, `ccb` and `castr`.
- Therefore take **memory and CPU for both servers from Railway's service metrics**, which is the
  same source for both. Use Rust's `process_*` only as a cross-check. Use the bench Redis counters
  above, not `upstreams`, to compare cache behaviour across servers.
- Server-side quantiles come from the fixed buckets (`.005 ... 20` s) and are coarse; use the mean
  there and k6's latencies as the headline numbers.

### Railway CPU and memory

For each run, take `loadStartedAt` and `loadEndedAt` from the `run` line (UTC), or a step's own
`startedAt` / `endedAt`, and read the target service's CPU and memory over that window: the
dashboard (Metrics, custom time range), the Railway MCP `get-service-metrics` tool, or the Railway
public API. Step windows are derived from when setup returned, so allow a second or two of slack.
Record peak and average. For `idle`, use the 30-minute window.

### Other measurements

- **Image size.** Build both images locally from a clean checkout of each branch and read the size:
  `docker build -f apps/server-rs/Dockerfile -t rs .` and `docker build -f apps/server/Dockerfile
  -t ts .`, then `docker image inspect --format '{{.Size}}' rs ts`.
- **Build time.** The Build step duration in each Railway deployment (note whether the cache was
  warm), and the `image` job in the `server-rs` workflow.
- **Cold start.** Railway keeps the old deployment serving until the new one is healthy, so polling
  `/readyz` during a redeploy measures nothing. Use the deployment timeline in the dashboard
  (deploy start to healthy), and the server's own first log line to its listening line.

## 7. Troubleshooting

| Symptom | Cause and fix |
|---|---|
| `setup()` fails: `TARGET_URL is refused` | The URL names a denied host (live `hccna-backend`, a production domain). Use the bench service |
| `setup()` fails: `.../readyz answered no response (dial ...)` | Target down, wrong name, or the IPv6-only private network (section 0). Use public domains |
| `setup()` fails: `anonymous sign-up failed: HTTP 400` or `403` | Wrong or restricted `FIREBASE_WEB_API_KEY`, or anonymous sign-in disabled in the project |
| `setup()` fails: discovery found no campuses | The server cannot reach Strapi, or authentication fails; check its logs |
| `setup()` fails: the run plans N sermon requests but only M pairs exist | Fewer sermons than the run needs distinct requests for. Lower `RATE` or `DURATION_SECONDS`, or raise `CURSOR_LIMIT` |
| `INVALID RUN` with dropped iterations | The generator or the network could not hold the rate. Lower the rate or check `hccna-bench` limits. Do not report the run |
| `INVALID RUN`: `graphqlOkRate` below 1 | Read the first warnings in stderr (reason, status and the start of the body). `typed-error:...` means a `FetchError` / `NotFoundError` result (an upstream is down or empty); 429 means the rate limit variable did not apply; 401 means token problems |
| `INVALID RUN`: not fresh | Cold run on a server that had served GraphQL. Flush Redis and restart the target, run nothing against it in between (`diff.ts` counts) |
| `server` line has `error` | `TARGET_METRICS_URL` unset or unreachable. Latency numbers are still valid |
| TS service crash-loops at boot | A required variable is missing (the log names it); add that one variable as a reference |

## 8. Cleanup

When the numbers are recorded:

1. **Point the gateway back at production first, and prove it forwards there.** Set
   `TS_ORIGIN_URL` on `hccna-backend-rs` to production's private domain, so it forwards to
   production `hccna-backend` again. Do not delete the variable instead. Unset, the gateway falls
   back to TS's public domain, where Railway's edge rewrites `X-Forwarded-For`, so all forwarded
   traffic would share TS's rate limits
   (`docs/superpowers/specs/2026-10-14-server-rs-parity-design.md`, "Rate limits behind the
   gateway"). What the second command prints must contain `hccna-backend` and not
   `hccna-backend-ts-bench`:

   ```sh
   railway variables --service hccna-backend-rs --environment production \
     --set 'TS_ORIGIN_URL=http://${{hccna-backend.RAILWAY_PRIVATE_DOMAIN}}:${{hccna-backend.PORT}}'
   railway variables --service hccna-backend-rs --environment production --json | jq -r '.TS_ORIGIN_URL // "unset"'
   ```

   Setting the variable starts a new deployment. Until it is healthy, the old one keeps serving,
   still pointed at the bench copy. Re-run this until it prints `SUCCESS` with a `createdAt` after
   the moment you set the variable. Stop and read the deploy log if it prints `FAILED` or
   `CRASHED`:

   ```sh
   railway deployment list --service hccna-backend-rs --environment production --limit 1 --json | jq -r '.[0] | "\(.status) \(.createdAt)"'
   ```

   Then send one forwarded request and confirm production answered it.
   `mutation ForwardCheck { __typename }` is always forwarded and changes nothing. TS adopts the
   `x-request-id`, so the id finds the request in each service's log:

   ```sh
   RS_URL=https://<rs domain>
   RID="bench-cleanup-forward-$(date +%s)"
   curl -s -H 'content-type: application/json' -H "x-request-id: $RID" \
     --data '{"query":"mutation ForwardCheck { __typename }"}' "$RS_URL/graphql"; echo
   sleep 5
   railway logs --service hccna-backend-rs --environment production --since 5m --json -n 5000 | grep -F "$RID"
   railway logs --service hccna-backend --environment production --since 5m --json -n 5000 | grep -cF "$RID"
   railway logs --service hccna-backend-ts-bench --environment production --since 5m --json -n 5000 | grep -cF "$RID"
   ```

   All of these must hold:
   - The response has `"__typename":"Mutation"` under `data` and no `errors`.
   - The Rust log line shows `route` as `forward` and `upstreamStatus` as 200.
   - The `hccna-backend` count is at least 1, and the `hccna-backend-ts-bench` count is 0. TS
     also logs `Unknown GraphQL operation observed (log-only)` for `ForwardCheck`; that is
     expected.

   **Do not go on to step 2 until they do.** A gateway still pointed at a deleted service answers
   every forwarded request with a 502.
2. Delete `hccna-bench`, `hccna-backend-ts-bench` and `hccna-bench-redis` (service Settings,
   Delete), or remove their deployments, so they stop costing money. Deleting the Redis service also
   removes its TCP proxy. `hccna-backend-rs` stays: it is the long-lived parity service
   (`docs/superpowers/specs/2026-10-14-server-rs-parity-design.md`).
3. Leave the `SERVER_RS_DEPLOY_ENABLED` variable set: `hccna-backend-rs` keeps deploying from `main`.
4. Delete the anonymous Firebase users the runs created: Authentication, Users, provider
   Anonymous, created inside the benchmark window. Note the window in `RESULTS.md`.
5. Confirm `hccna-backend` has no new deployments and `api.hccnj.org` is unchanged.
6. Last, clean up locally. Unlink the CLI, now that no `railway` command is left to run:
   `railway unlink` in the checkout you linked in section 0, and in the `main` worktree
   (`( cd "$TMPDIR/hccna-main" && railway unlink )`). Then remove the worktree
   (`git worktree remove "$TMPDIR/hccna-main"`) and delete `$TMPDIR/bench/` and the diff report
   directories: they hold production-derived content, and the repository rules forbid keeping real
   data in the checkout. Unset `FIREBASE_WEB_API_KEY` and `BENCH_REDIS_URL` in your shell.
