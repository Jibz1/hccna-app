# Monthly notification recovery

`lastUpdate` records when the monthly WOA was assigned, independently of notification delivery. `wordOfActivationMonthly` first assigns the current month's verse to every eligible subscription and commits `wordActivationId` and `lastUpdate`. The same transaction records pending email and push work in `monthlyDelivery`. All assignment attempts finish before notification processing starts, so a slow provider, failed send, or delivery-lease UUID failure cannot hold back the WOA shown in the app.

A new month replaces obsolete pending notifications and their leases immediately. Only the current month's delivery is retried, using the already assigned verse. An older worker cannot acknowledge or overwrite a newer delivery, and a delayed rotation cannot roll a newer month's assignment back. Members who have unsubscribed have pending channels cancelled.

Cloud Scheduler only starts the run: `wordOfActivationMonthly` returns `WordOfActivationRunStarted` immediately and the server's application scope owns the work. Each run retries its failed subscribers once, after one minute. Subscriptions still failing after that raise a single Sentry issue per month (tag `job:woa-delivery`) listing their profile IDs, never email addresses; a run that fails outright is reported with `captureException`. A subscriber can count as both `assigned` and `failed`: the WOA is available, but a notification operation failed. Push rejections for unregistered tokens are pruned and do not keep a push pending.

To resend, force-run the paused Cloud Scheduler job `WordActivationSendPending` (us-east4), which calls `wordOfActivationSendPending`. It claims only the current month's pending channels, never assigns verses, and gets the same single retry. Completed channels are skipped. Concurrent delivery attempts use a five-minute lease; a run interrupted by shutdown leaves its remaining channels pending, and its leases expire within five minutes. Delivery work has a two-minute timeout per subscriber.

Existing same-month records without `monthlyDelivery` are treated as completed to avoid resending historical notifications. Failed deliveries from before this change require an explicit operational review; they cannot be inferred from `lastUpdate`.

Notification delivery can repeat within the current month. A process can stop after a provider accepts a send but before Firestore records success, causing a retry to send it again. Retrying a partially failed push channel can also repeat pushes on devices that already accepted the first attempt. Notifications already in flight when a new month is assigned may still arrive, but cannot change the newer WOA or its delivery state. No provider-level exactly-once guarantee is assumed.
